작성일: 2026년 10월 28일, 한국 시간. 다음에 사용자가 **“이어서 작업해줘”**라고 하면 이 문서와 [개발 계획](NEXT_DEVELOPMENT_PLAN.md)을 읽고 첫 미완료 항목부터 구현한다. 날짜가 달라져도 별도의 재설명 없이 재개할 수 있도록 남긴 기록이다. 자동 실행이나 예약 작업은 설정하지 않았다.

## 재개할 때 먼저 할 일

1. 작업 위치 `D:\개인프로젝트\FreeFolder`, 게임 폴더 `pokemon_rl/`를 확인한다.
2. `git status --short`와 최근 커밋으로 사용자 변경·진행 중 작업이 있는지 확인한다. 아래 기준 커밋으로 되돌리지 않는다.
3. 이 문서의 체크 목록과 개발 계획에서 첫 미완료 작업을 찾는다. 현재 다음 작업은 **10a번 실제 탐험 밸런스 측정**이다.
4. 해당 작업의 최소 재현·회귀 검사부터 작성하고 구현한다. 기존 저장과 공용 전투 엔진 연결을 보존한다.
5. 작업 묶음별 검증 → 문서 상태 갱신 → 커밋·푸시 순서로 진행한다. 사용자가 이미 요청한 흐름이며, 최신 사용자 지시가 있으면 그것을 따른다.
6. 새로 발견한 차단 문제가 있으면 근거를 기록하고 우선순위를 조정한다. 불필요한 전체 재학습이나 완료 단계 재구현은 하지 않는다.

Windows에서 Git이 소유권 오류를 내면 전역 설정을 바꾸지 않고 다음 형태를 사용한다.


## 8번: 전투 캐시 회수

**해결한 문제:** 떠난 전투의 무기한 누적과 생성/복원 상한 불일치. 기본 상한 16개·유휴 300초를 생성과 restore에 공통 적용했다. 정리는 인증된 활동 시 실행하며 별도 타이머는 없다. 런 캐시만 대상이고 probe 임시 전투·자유전·멀티플레이는 이 한도에서 제외한다. 아래는 구현 때 확인한 조건과 회귀 기준이다.

**착수 순서**

1. 작은 테스트 상한과 가짜 monotonic 시계로 생성·복원 상한 및 유휴 전투 누적을 재현한다.
2. 생성과 복원이 같은 용량 확보 경로를 사용하도록 만든다. 유휴 시간·LRU와 실제 부하를 고려해 기본값을 정하고 현재 처리 중인 런을 제외한다.
3. 마지막 DB commit의 checkpoint를 보존하면서 해당 런의 메모리 전투만 퇴출한다. 복원은 그 checkpoint를 사용한다.
4. worker 교체·저장 실패·서비스 종료 시 접근 시각과 캐시 항목도 일관되게 정리한다.
5. 실제 엔진에서 퇴출·복원 후 같은 턴·HP·PP·도구·대기 입력·승패로 이어지는지 확인한다.

**반드시 유지할 조건**

- 진행 중 전투를 준비 단계의 `state.resources`로 새로 만들지 않는다. 미저장 worker 상태를 저장 checkpoint 위에 덮어쓰지 않는다.
- `owns_client=False`이면 해당 런의 `close_battle()`만 호출한다. 공용 `client.close()`나 worker 재시작으로 자유전·멀티플레이를 끊지 않는다.
- 캐시 회수 때문에 게임 진행·재화·플레이어 입력이 추가 적용되지 않아야 한다. 복원 과정의 저장으로 런 버전이 바뀌면 응답에는 최종 버전을 제공한다.
- DB 런·브라우저 접근정보를 삭제하는 기능과 구분한다.

**관련 파일:** `pokemon_rl/services/run_service.py`, `services/engine_api.py`, `server_core.py`, `server_deploy.py`, `battle_service/client.py`, `battle_service/engine.cjs`.

**완료 기준:** 생성·restore 모두 상한 준수, 퇴출 후 정확한 복원, 저장 실패 직후·worker 교체 복구, 공용 worker의 다른 모드 전투 유지, 보상·명령 중복 없음. 기존 `tests/test_run_storage.py`, `test_run_requests.py`, `test_run_service.py`와 실제 20구간 완주도 통과한다.

## 9a: 생성 응답 소실 복구

**해결한 문제:** 생성 응답이 소실돼 새 탐험 접근정보를 모르는 경우. 브라우저가 POST 전에 독립 pending 정보와 32byte 생성 ID·비밀값을 보관한다. 서버는 기존 PK와 안정적인 파생 자격증명으로 동일 런의 현재 상태를 회복한다. DB에는 원문 비밀값·토큰을 저장하지 않고 해시·요청 지문만 보관한다. 아래는 구현 때 확인한 조건과 회귀 기준이다.

**구현 순서**

1. 브라우저가 생성 전에 저장하는 고엔트로피 생성 자격증명과 서버의 멱등 조회 방식을 먼저 설계한다. 기존 토큰 해시에서 원문 토큰을 복구할 수 있다고 가정하지 않는다.
2. 생성 식별자·요청 지문·런 연결을 최초 런 생성과 같은 DB transaction으로 보관하고 동시 중복을 방지한다. 메모리 캐시만으로 해결하지 않는다.
3. 같은 식별자·같은 요청은 같은 런과 유효한 접근정보를 반환한다. 다른 파티·난이도·시드는 충돌 처리하고, 생략된 seed는 최초 한 번만 생성한다.
4. 브라우저 재로드·재시도는 pending 요청을 재사용한다. 새 탐험을 의도적으로 만드는 요청에는 새 식별자를 발급한다. 이미 진행된 탐험의 재시도는 최신 상태를 반환한다.
5. 원문 자격증명을 URL·로그·공개 상태에 노출하지 않고 구형 저장·온라인 백업·복원을 유지한다.

**관련 파일:** `services/run_service.py`, `services/run_api.py`, `services/save_tools.py`, `services/save_format.py`, `web/rogue-client.js`, 저장·HTTP·프론트 검사.

**주의할 실제 제약:** 현재 저장 검사기는 `runs` 외 추가 테이블·뷰·트리거 등을 비호환으로 처리한다. 새 DB 객체를 도입하면 검사기와 마이그레이션·백업·복원을 함께 갱신한다. 현재 런 토큰을 단순히 평문으로 추가 저장해 해결하지 않는다.

**완료 기준:** commit 전후 응답 소실, 동시 중복 POST, 서버 재시작·페이지 재로드, 다른 요청 내용 충돌, pending 정보 보존, 기존 저장과 백업·복원 호환을 검사하고 실제 브라우저에서 같은 런을 회복한다.

## 9b: 탐험 결산과 구간 기록

**해결한 문제:** 결과의 자원 소비와 선택을 되돌아볼 수 있도록 상태와 같은 commit에 기록·집계를 저장한다. 상세는 최근 128개, 누적 집계는 전체 기록 범위를 유지한다. 아래는 유지할 회귀 조건이다.

- 서버에서 구간 종류·선택한 분기·전투 턴·전후 HP/PP·기절·골드 수입/지출·보상·회복·영입을 필요한 범위로 기록한다.
- 기록과 집계는 게임 상태와 같은 commit으로 보관한다. 명령 재시도·resume·캐시 복원에서 기록을 중복 생성하지 않는다.
- 기록 크기에 상한을 두고 비공개 상대 빌드·checkpoint·접근 토큰은 결과 API에 내보내지 않는다.
- 완주·패배 화면에 진행 구간, 파티·특전, 자원 소비와 주요 선택을 표시하고 최근 탐험에서 다시 열 수 있게 한다.
- 구형 탐험의 없는 과거 기록을 추정해 생성하지 않는다. 기록 시작 이후 범위와 미기록 상태를 표시한다.

**검증:** 새 기록 helper·서비스 29개, 저장 도구 27개 중 26개 통과·Windows 권한 검사 1개 건너뜀, Node 전체 141개 통과. 실제 엔진의 20구간 65이벤트·온라인 백업/복원·종료 저장 실패 후 1회 반영을 확인했다. 브라우저의 기존 탐험 부분 기록과 새 탐험 전체 기록 결과를 360px 이미지로 확인했다. 전투 중 기술 회복은 별도 집계하지 않으며 누적 회복은 보상·쉼터·상점과 실제 전투 후 특전의 증가량이다.

## 10a/10b: 밸런스 측정 후 조정

1. 먼저 기준 파티·합법 의사결정 정책·seed 목록·최대 턴/입력 수와 지표를 고정한다. 첫 측정은 같은 20개 seed × 기본/전략 두 모드, 총 40런을 출발점으로 삼는다.
2. 구간별 도달률·패배 위치·HP/PP 소모·기절·회복·재화와 실제 실행 조건을 보고서에 남긴다. HP·승패·DB 진행 단계를 조작하지 않는다.
3. 이것은 특정 자동 정책의 결과이며 실제 사용자의 완주율이 아니다. 기존 3대3 AI 평가 승률과도 구분한다.
4. 병목을 확인한 뒤 회복 배치·가격·보상·상대 구성·분기 차이를 작은 묶음으로 조정하고 같은 조건으로 전후 비교한다.
5. 콘텐츠 변경으로 기존 런이 비호환 오류만 내지 않도록 이전 콘텐츠 지원 또는 명확한 호환 설계를 함께 구현한다. `content_version` 변경과 저장 보존을 검토한다.
6. 콘텐츠 확장과 추가 신경망 학습은 그 근거를 확보한 뒤 진행한다. 이미 공개한 최종 AI test에 맞춘 재학습·후보 재선택은 하지 않는다.

- 저장 형식 `SAVE_VERSION=1`, 콘텐츠 `roguelike-v1`. HTTP 변경은 최상위 `run_revision`을 요구하고, 각 전투의 `battle.revision`은 별도다. 오래된 입력은 409 `RUN_STALE`, `/resume`은 버전 없이 인증 후 가능하다.
- 선두 변경은 전투 준비에서 팀·자원을 함께 재배열한다. 회복 미리보기는 실제 적용 함수와 공유하며 구형 저장·소모 도구·수면·타입 폼 메타를 보존한다.
- 최근 탐험은 런별 독립 브라우저 키와 제거 표식을 사용한다. 10개는 신규 생성 제한이며 동시 생성으로 11개가 된 기존 접근정보를 자르지 않는다.
- 최신 코드는 원격 `origin/main`에 푸시돼 있었다. 다음 실행에서는 실제 Git 상태를 다시 확인한다. 원격은 `https://github.com/dndjd321/FreeFolder.git`이다.
- 이전 로컬 QA 서버와 Ego 작업공간은 종료했다. 검사에 필요하면 새 QA 저장 경로와 새 브라우저 작업공간을 사용한다. `pokemon_rl/runtime/`의 예전 QA 저장·접근정보는 Git에 올리지 않는다.

## 검증과 실행 진입점

명령은 저장소 루트에서 실행한다. 설치·배포의 세부 사항은 [배포 안내](DEPLOYMENT.md)를 따른다.

```powershell
python -X utf8 -B -m unittest discover -s pokemon_rl/tests -p 'test_run*.py' -v
node --test pokemon_rl/tests/rogue_frontend.test.cjs

# 서버·저장·엔진을 바꾼 작업 묶음의 최종 통합 검사
$env:OMP_NUM_THREADS='1'
$env:MKL_NUM_THREADS='1'
python -X utf8 -B -m unittest discover -s pokemon_rl/tests -p 'test_*.py' -v
node --test pokemon_rl/tests/*.test.cjs
```

Node 의존성이 없으면 `npm --prefix pokemon_rl/battle_service ci --ignore-scripts`로 고정 버전을 설치한다. 기본 서버 의존성은 `pokemon_rl/requirements.txt`, 전체 학습 검사 의존성은 `requirements-training.txt`다. 기본 서버에 신경망을 사용하지 않으면 PyTorch는 필요 없다. 전체 학습 검사를 할 환경은 배포 안내의 CPU 설치 절차를 따른다.

브라우저 검사용 서버는 `FREEFOLDER_SAVE_DIR`를 새로운 `pokemon_rl/runtime/` 하위 QA 경로로 설정한 뒤 `pokemon_rl/`에서 `python -X utf8 -B -m uvicorn server_deploy:app --host 127.0.0.1 --port 18768 --no-access-log`로 실행할 수 있다. 포트 사용 여부를 먼저 확인한다. 서버·Node 자원을 정리하고 브라우저 작업공간은 검사 종료 후 닫는다.

GitHub Actions `.github/workflows/tests.yml`이 Linux 전체 검사와 Docker 검증을 수행한다. 로컬 Docker는 이전 작업 시 설치되어 있지 않았다. 해당 변경의 CI 결과와 운영 서버의 필요한 응답·스크립트만 확인하고 검증 기록을 남긴다. 문서만 바꾸는 날에는 게임 테스트를 불필요하게 다시 실행하지 않는다.

## 당장 먼저 고치지 않아도 되는 후속 항목

- 같은 런의 브라우저 요약은 매우 짧은 동시 쓰기 경쟁에서 과거 상태로 표시될 수 있다. 접근정보와 서버 진행은 보존되며 재개 시 최신 상태를 읽는다. 접근정보 손실과 구분하고 필요 시 별도 수정한다.
- 이전 모바일 검증은 360/390px DOM 폭·버튼 높이·행동 검증이었다. 창 최소화로 최종 이미지 캡처를 하지 못했으므로 향후 화면 변경 시 실제 시각 검증을 보완한다.
- 운영 저장의 영속 디스크·외부 백업 보관은 도구 구현과 별도 운영 설정이다. 자동으로 보장됐다고 기록하지 않는다.
- 실험 신경망은 30종 재학습 후보다. 이전 bootstrap 상대 확인 승률 70.2%였지만 규칙 AI 상대는 19.8%이므로 규칙 AI를 계속 권장한다. 기본 Docker/운영 서버에는 신경망이 없다. [평가 규약](AI_EVALUATION_PROTOCOL.md)과 [학습 기록](../pokemon_rl/training/README.md)을 보존한다.
